:::task{num="1" ar="تعارض سطر واحد" en="Single-line conflict" pts="20" level="إتقان"}

**الشكل الصحيح للتعارض الذي يجب أن ينتجه الطالب:**
```text
<<<<<<< HEAD
شعار الفريق: «نتعلّم معاً، ونرفع معاً» — أعضاء الفريق: سارة
=======
شعار الفريق: «نتعلّم معاً، ونرفع معاً» — أعضاء الفريق: عمر
>>>>>>> docs/omar-slogan
```

**الحل النموذجي:**
```text
شعار الفريق: «نتعلّم معاً، ونرفع معاً» — أعضاء الفريق: سارة، عمر

$ git add sandbox/team-slogan.txt
$ git commit --no-edit
[main d34a3f6] Merge pull request #22 from omar/slogan
$ git diff --check          # لا مخرجات
```

**سلّم تقييم الحل (20 نقطة):**

| العنصر | النقاط |
|---|---|
| أنتج تعارضاً حقيقياً (مخرجات `CONFLICT (content)`) | 5 |
| الصق مقطع العلامات كما ظهر على شاشته | 4 |
| السطر النهائي النظيف بلا أي علامة | 5 |
| `git add` ثم `git commit --no-edit` ثم نجاح الإكمال | 4 |
| `git diff --check` بلا مخرجات (تحقّق ذاتي) | 2 |

**أخطاء متوقعة وخصوماتها:**

| الخطأ | النتيجة في المشروع | الخصم |
|---|---|---|
| اختار نسخته فقط وحذف اسم الزميل | ضياع مساهمة زميل | −8 (خلل تعاوني) |
| بقيت `<<<<<<< HEAD` داخل الملف | المشروع مكسور | −10 إذا لم يلاحظها، −3 إن أصلحها بعد `diff --check` |
| `git add` منسي ثم `git commit` | `nothing to commit` | لا خصم إن فهم السبب وسأل |
| استخدم `git merge --abort` ثم أعاد المحاولة | سلوك صحيح ومحمود | لا خصم |
| حلّل التعارض بتحرير النص في VS Code | الأسهل والأفضل | لا خصم، بل شجّعه |

:::box{type="err" ar="فحص إلزامي بعد كل حل تعارض (لا تُسلّم ورقة بلا هذا الفحص)" en="Mandatory post-resolution check"}
```text
$ grep -rn "<<<<<<<\|>>>>>>>\|=======" --include="*.json" --include="*.txt" --include="*.md" .
$ git diff --check
```
إن ظهر أي ملف فيه علامات، فالمشروع **مكسور** ويجب ألا يُقبل التسليم.
:::
:::

:::task{num="2" ar="تعارض الملف المُولَّد" en="Generated-file conflict" pts="20" level="إتقان"}

**الحل الصحيح الوحيد (وهو مقياس فهم الورقة):**
```text
$ node tools/build-index.mjs
[build-index] ✓ تم توليد الفهرس: 5 بطاقة.
   • example-student  • leen-docs  • omar-qa  • sara-design  • you-instructor

$ git add data/members-index.json data/members-bundle.js
$ git rebase --continue
[detached HEAD 9a8b7c6] feat(members): add card for omar-qa
Successfully rebased and updated refs/heads/feature/omar-qa-card.
```

**أخطاء متوقعة وخصوماتها:**

| الحل الذي كتبه الطالب | التقييم | الدرجة |
|---|---|---|
| أعد التوليد ثم `add` ثم `rebase --continue` | **الحل الاحترافي** | 20 |
| حلّ التعارض يدوياً بكتابة السطرين معاً (`"leen-docs.json", "omar-qa.json",`) | ينجح الآن ويفشل لاحقاً — ناقص المفهوم | 12 |
| ألغى `rebase` كاملاً (`--abort`) وأعاد العمل من الصفر على فرع جديد | مقبول عدا خسارة تجربة | 14 |
| اختار نسخته وحذف مدخل الزميل | يتسبب باختفاء بطاقة زميل من الموقع | **−10** |
| لم يفرّق بين `rebase --continue` و`merge --continue` | خطأ إجرائي | −3 |
| لم يفهم لماذا الحدث (لماذا هذا الملف مشترك) | يكرر الخطأ | تعليق إلزامي في التقييم |

:::box{type="tip" ar="السؤال الذي يفرز الفهم" en="The separating question"}
اسأل: «لماذا كان حلّ `members-index.json` يدوياً صحيحاً تقنياً وخطأ منهجياً؟» الإجابة
الكاملة: «لأن الملف **نتيجة** لا مصدر — تولّده الأداة من محتوى المجلد. وأي تعديل يدوي
سيُطمس عند التوليد التالي، وقد يبقى مدخل زميل ناقصاً بلا أن يلاحظ أحد.» من أجاب بهذا
المنطق فهو جاهز لقيادة فريق.
:::
:::

:::task{num="3" ar="rebase والدفع الآمن" en="Rebase and safe push" pts="15" level="فهم أمني"}

**الإجابة النموذجية:**
```text
$ git push
 ! [rejected]        feature/omar-qa-card -> feature/omar-qa-card (non-fast-forward)
...
$ git push --force-with-lease origin feature/omar-qa-card
 + 1af7c9b...9a8b7c6 feature/omar-qa-card -> feature/omar-qa-card (forced update)
```

**معيار القبول (15 نقطة):**
| العنصر | النقاط |
|---|---|
| مخرجات رفض الدفع العادي (`non-fast-forward`) | 4 |
| نجاح `--force-with-lease` صحيح الصيغة | 4 |
| شرح أن الآلية تقارن بحالة الفرع البعيد المعروفة محلياً وترفض إن تغيّرت | 5 |
| ذكر أن الصلاحية **للفرع الشخصي فقط** وليست لـ `main` | 2 |

**أخطاء متوقعة:**

| الخطأ | الخطورة | الخصم |
|---|---|---|
| استخدم `git push --force` | خطر فقدان عمل زميل | **−8** + إعادة تدريب |
| نفّذ `--force` على `main` | مخالفة جسيمة | **−15 وإبلاغ** |
| قال «الفرق أن with-lease أطول» | لم يفهم | 0 في سؤال الشرح |
| استخدم `git push -f` على فرع زميل | سلوك مرفوض | **−10** |
| لم يلاحظ `ahead 1, behind 3` | لا يعرف قراءة الحالة | −3 |

:::box{type="warn" ar="درس أمني أوسع — اربطه بالمشروع" en="Wider security lesson"}
هذه أول مرة يرى فيها الطالب أن «القوة» في Git قد تدمّر عمل غيره — وهو نفس المنطق في
`git clean -fd` و`git reset --hard` و`git branch -D`. اجعل القاعدة صريحة على السبورة:

**«أوامر القوة المدمّرة: للفرع الشخصي فقط، وبعد التحقق، ومع نسخة احتياطية من العمل.»**
:::
:::

:::task{num="4" ar="الفحوص الستة قبل المراجعة" en="Six pre-review checks" pts="15" level="منهج"}

**الإجابات النموذجية:**

| # | الأمر | النتيجة الصحيحة |
|---|---|---|
| 1 | `node tests/validate-members.mjs` | `0 خطأ، 0 تحذير` |
| 2 | `git diff --check` | لا مخرجات |
| 3 | `git diff --stat origin/main...HEAD` | ملفات البطاقة + الفهرس + الـ bundle فقط |
| 4 | `git log --oneline origin/main..HEAD` | التزام (أو التزامات) بصيغة صحيحة |
| 5 | `git status -sb` | لا `behind`، ولا `diverged` |
| 6 | `git diff origin/main...HEAD | grep -iE "token\|password"` | لا نتائج |

**معيار القبول:** 2.5 نقطة لكل فحص منفّذ بمخرجات أو بنتيجة مذكورة. الفحص 6 هو **الأهم
أمنياً**؛ من تركه فارغاً بلا سبب ⇒ لا تُمنح نقاطه حتى لو نجحت الفحوص الأخرى، لأن الدرس
الأمني مقصود ولا يمكن تقييم غيره مكانه.

**أخطاء متوقعة:** من كتب `git diff main..HEAD` (نقطتان) بدل `...` (ثلاث) فيظهر الفرق
معاكساً ← وجّهه؛ لا تخصم في بند الفحوص لكن اذكرها ملاحظة. من نفّذ `git fetch` أولاً قبل
المقارنة ← ممتاز، أضف نقطة تقدير (bonus) وسجّلها.

:::box{type="info" ar="استثمار تعليمي: اجعل الفحص عادة" en="Turn checks into habit"}
اطلب في كل ورقة قادمة (ولو بنداً واحداً) تنفيذ الفحص `git diff --check` قبل أي التزام.
الطلاب الذين يبنون عادة «افحص قبل أن ترفع» يعودون من أي جلسة عمل بلا مفاجآت — وهذه
المهارة تنقلهم من «متعلمين» إلى «موثوقين».
:::
:::

:::task{num="5" ar="النشر على GitHub Pages" en="Deploy to GitHub Pages" pts="15" level="تنفيذ"}

**الإجابة النموذجية:** رابط من الصيغة `https://<org>.github.io/class-team-hub/` يعمل،
وتظهر فيه كل بطاقات الفريق.

**معيار القبول:** 10 نقاط لرابط يعمل ويفتح الشاشة الرئيسية؛ 5 نقاط لظهور **بطاقة الطالب
نفسه** بين البطاقات (فلا تظهر صورة شاشة للصفحة الرئيسية فقط).

**أخطاء متوقعة ومصفوفة تشخيص سريعة للمدرّب:**

| العرض في الرابط | السبب الفعلي | علاج فوري في الجلسة |
|---|---|---|
| `404` ثابت بعد 5 دقائق | لم يُفعَّل Pages أو المسار خطأ | Settings ← Pages ← Branch: `main` / Root ثم Save |
| الصفحة تعمل بلا أي بطاقة | `fetch` فشل بسبب مسار غير مطابق للأحرف | افتح F12 → Console واقرأ الرسالة الحمراء |
| تظهر بطاقات قديمة (من ضمنها مثال) | `main` لم يُحدَّث بالدمج | `git pull` ثم فحص الدمج على المستودع |
| تظهر بطاقات لكن نقص عددها | بطاقة فيها JSON خطأ | `node tests/validate-members.mjs` على جهاز المدرّب |
| الصفحة بيضاء تماماً | تعارض دُمج وترك آثاراً | `grep -rn "<<<<<<<" --include="*.js" --include="*.html" .` |
| يعمل لديه ولا يعمل للزائر | نسي `Commit` لـ `members-index.json` | أعد التوليد والتزم وارفع |

:::box{type="tip" ar="لحظة تحفيزية استخدمها" en="Use the motivational moment"}
اجعل الطالب يفتح رابط الموقع المنشور ويُري **بطاقته** لوالده أو صديقه أو يرسلها في
مجموعة الصف. هذه اللحظة («عمل منشور على الإنترنت باسمي، وفريق عمل عليه معي») أقوى محرّك
لتعلم المزيد من عشر محاضرات. خصّص لها دقيقتين في نهاية الجلسة.
:::

:::task{num="6" ar="طلب السحب النهائي والتقرير" en="Final PR and report" pts="15" level="إتقان"}

**معيار القبول للطلب (7 نقاط):** عنوان بصيغة صحيحة، الوصف يشمل `Closes #<issue>`، طريقة
الاختبار موثّقة بمخرجات `validate-members`، وطلب مراجعة من زميل، وتقديم ملف واحد فقط
(`README.md` غالباً) بلا خلط مهام.

**معيار القبول للتقرير (8 نقاط):** أن تكون كل القيم حقيقية وقابلة للمطابقة مع المستودع.
تحقّق ذكياً من سطرين فقط: (1) عدد البطاقات = عدد ملفات `data/members/*.json` ناقص
القالب والمثال والمدرّب؛ (2) عدد الالتزامات في `main` يقارن بـ `git log --oneline main | wc -l`
على النسخة المشتركة. التقرير المتفق مع الواقع = درجة كاملة.

**أخطاء متوقعة:**
- أرقام بلا أي مقابل واقعي (توحي بالتقدير) ← −3 مع إعادة الطلب.
- «أكبر تعارض واجهته» مكتوب نظرياً («التعارض يحدث عندما…») بدل تجربته ← −2.
- لا ذكر لأي فرع فشل في دمجه (يبدو الكمال غير الواقعي) ← لا خصم لكن شجّع الصدق.
- PR نهائي يخلط ثلاثة ملفات مختلفة (README + CSS + بطاقة) ← −2 (خلط مهام).

:::box{type="ok" ar="بوابة الإتمام النهائي — افحصها بنفسك لا بتقرير الطالب" en="Final completion gate"}
```text
1) افتح رابط GitHub Pages:  بطاقة الطالب ظاهرة هناك؟            ☐
2) main متساوٍ مع origin/main على جهاز الطالب (git status)      ☐
3) node tests/validate-members.mjs  →  0 خطأ                     ☐
4) عدد طلبات السحب التي أنشأها الطالب ≥ 3 (له/مراجعة/أُغلقت)      ☐
5) لصق دليلين مختلفين لحل تعارضين (سطر + مُولَّد) في الورقة        ☐
6) لا آثار للعلامات: grep -rn "<<<<<<<" .  →  لا نتائج            ☐
7) لا أسرار في المستودع: grep -rniE "token|password|secret" بالمجات ☐
```

:::task{num="س1" ar="لماذا تعارض في نفس السطر فقط" en="Why same-line conflicts" pts="4" level="تحليل"}
**الجواب:** Git يدمج على مستوى **الأسطر والكتل**، لا الملفات. عند تعديل أسطر متباعدة، كل
تعديل يقع في «مقطع» مختلف من الملف فيدمجهما تلقائياً بلا تداخل. أما تعديل نفس السطر من
الجهتين فينتج **مقطعان متعارضان** لنفس الموضع، ولا يستطيع Git تخمين أيّهما المقصود —
فيتوقف ويسلّم القرار للإنسان.
:::

:::task{num="س2" ar="معنى HEAD في merge مقابل rebase" en="HEAD in merge vs rebase" pts="4" level="تحليل"}
**الجواب:** في تعارض **merge**: `HEAD` يمثّل فرعك الحالي (المتلقّي)، والطرف الآخر هو
الفرع الذي تحاول دمجه — أي «نسختي» مقابل «القادم». أما في تعارض **rebase**: يعمل Git على
حالة `HEAD` منفصلة (detached)، وفيها `HEAD` يمثّل **الفرع الذي تُبنى عليه** (أي `main`
الجديد غالباً)، والطرف الآخر هو التزامك الذي يعيد تشكيله — أي أن المعنى **معكوس**.
هذا هو سبب أخطاء الطلاب الشائعة: يظنّون سطر `HEAD` نسختهم دائماً فيختارون الطرف الخطأ
ويضيع عملهم.
:::

:::task{num="س3" ar="لو كان الفهرس يدوياً" en="If the index were manual" pts="4" level="تحليل"}
**الجواب:** «كان كل طالب سيعدّل نفس الملف في نفس الموضع تقريباً، فيقع تعارض في كل طلب سحب
تقريراً، ويحتاج كل دمج إلى تدخل بشري. ومع 20 طالباً كان تاريخ `main` سيصبح سلسلة تعارضات
يُحلّ بعضها بالخطأ (حذف مدخل زميل، أو تكراره، أو خروج ترتيب الملف)، وتزداد أخطاء JSON
ويصبح رفع البطاقة عملية مرهقة بدل أن تكون بسيطة.» **الخلاصة:** لكي يعمل الفريق، اجعل
الملفات المشتركة أقل ما يمكن، واستخدم ملفات فردية + توليد آلي.
:::

:::task{num="س4" ar="تعديل مقترح على سير العمل" en="Workflow improvement proposal" pts="3" level="قيادة"}
**إجابات ممتازة مقبولة:**
- تفعيل **Code Owners** بحيث لا يُدمج تعديل ملف مشترك إلا بمراجعة قائد الفريق.
- توحيد الاجتماع اليومي القصير (Stand-up) لمزامنة الفروع قبل بدء العمل.
- قاعدة: «لا فرع يعيش أكثر من يومين» — لتقليل التعارضات.
- إضافة أداة فحص تلقائي (GitHub Actions) تشغّل `validate-members` على كل طلب سحب،
  فيرفض الطلب آلياً قبل أن يصل للمراجعة البشرية.
- تخصيص ملف واحد لكل طالب دائماً، وأي تعديل جماعي يُوضع في ملف جديد لتفادي التعارض.

**معيار الدرجة:** نقطتان لفكرة عملية قابلة للتنفيذ في المشروع + نقطة لربطها بتقليل
التعارضات تحديداً. الفكرة العامة («نتعاون أكثر») بلا آلية ⇒ نقطة واحدة.
:::

|---|---|

| **إتمام متقدم** | 85+ في المجموع، مع 3 طلبات سحب (له/راجع/أُغلق بالمراجعة) ودليل حل تعارضين |
| **قائد فريق مدرب** | إتمام متقدم + مراجعات مكتوبة عالية الجودة لثلاثة زملاء + تقرير مشروع بأرقام دقيقة، وحل تعارض زميل عملياً أمام المجموعة |
