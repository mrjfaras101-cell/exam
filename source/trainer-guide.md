:::band{ar="1 · فلسفة البرنامج ونتائجه" en="1 · Programme philosophy & outcomes"}
:::

:::bi
البرنامج مبني على مبدأ واحد: **يُتعلّم Git بالعمل الجماعي فقط**. لذلك يبدأ كل طالب
بعمل خاص به (بطاقته)، ثم يرى عمل زملائه، ثم يواجه تعارضاً حقيقياً ويحلّه، ثم يُنشَر
النتيجة للعالم. في نهاية البرنامج يكون المتدرب قادراً على العمل كعضو فريق في مستودع
حقيقي — لا أن يحفظ أوامر فقط.
---EN---
The programme rests on one principle: Git is learned through real collaboration. Each trainee
owns a personal artefact (their card), sees teammates' work, resolves a genuine conflict, and
ships the result publicly.
:::

**النتائج التدريبية المتوقعة (Measurable outcomes):**

| # | النتيجة | كيف تُقاس |
|---|---|---|
| 1 | إنشاء حساب ومستودع وإعداد بيئة عمل مؤمَّنة | ورقة 01 — الأدلة السبعة |
| 2 | استنساخ مشروع حقيقي وفهم بنيته وتشغيله محلياً | ورقة 02 — دليل التشغيل + جدول البنية |
| 3 | مساهمة كاملة: فرع → التزام → رفع → طلب سحب → مراجعة | ورقة 03 — رقم PR + مراجعة مكتوبة |
| 4 | مزامنة عمل الفريق وفهم استراتيجيات الدمج | ورقة 04 — مخرجات الدمج + تقرير الفريق |
| 5 | حل التعارضات بأمان والنشر على الإنترنت | ورقة 05 — دليل تعارضين + رابط منشور |

:::box{type="tip" ar="مبدأ التصميم التربوي" en="Instructional design principle"}
كل ورقة = دورة تعلّم كاملة: **مفهوم قصير → تنفيذ على الجهاز → دليل مخرجات → تحقّق ذاتي
→ تسليم**. لا يوجد بند نظري بلا تنفيذ مقابله، ولا تنفيذ بلا دليل يثبته. هذا يقلّل
«الحفظ الأعمى» ويمنحك أنت أدلة قابلة للمطابقة.
:::

:::box{type="info" ar="الوحدة المتقدمة (السادسة) — لمن ومتى؟" en="The advanced unit"}
الورقة 06 **ليست إلزامية للجميع**. اعرضها على:
1. من أنهى الأوراق الخمس بنتيجة 85+ (تحدٍّ مناسب بلا إحباط).
2. الطلاب الذين يظهرونهم بشكل متكرر — بمعنى آخر: من يصبح **مصدر خطأ متكرر** للفريق،
   إذ تحلّ الآلة محلّ إرشادك المتكرر.
والقاعدة التربوية: امنح هذه الوحدة كـ**مسؤولية** («أنت المسؤول عن جودة المشروع الآن»)
لا كمكافأة، فتتحول من «واجب إضافي» إلى **منصب** يريدونه.
:::

:::box{type="warn" ar="إدارة الوقت — أشد مشكلة في هذه الورشة" en="Time management"}
90% من التأخير سببه طالب واحد عالق في تثبيت أو أمر خاطئ. الحلول المجرَّبة:
1. **زميل مساعد**: عيّن الطالب الأسرع «مساعد الجلسة» يتحرك بين الصفوف (وليست مهمة إدارية بل تدريبية).
2. **مهل زمنية مرئية**: اكتب على السبورة وقت نهاية كل مهمة، ونادِ عند الانتقال.
3. **لا تحلّ جهاز طالب بيدك**: اسأل «ماذا تقرأ في هذه الرسالة؟» واتركه ينفّذ.
4. **شريحة زمن احتياطية**: اترك آخر 10 دقائق بلا محتوى جديد دائماً.
:::

:::check{ar="قبل اليوم الأول بثلاثة أيام" en="Three days before"}
- [ ] ارفع نسخة المشروع `class-team-hub` إلى منظمة GitHub خاصة بالورشة (مثال: `school-git-workshop`)
- [ ] فعّل حماية الفرع: `Settings ← Branches ← main ← Require a pull request before merging`
- [ ] ارفع إلى المنظمة ملفات القالب: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `.github/PULL_REQUEST_TEMPLATE.md`
- [ ] جهّز تفعيل GitHub Pages (بعد الجلسة الخامسة) واختبر الرابط بمشروع تجريبي
- [ ] اختبر الحساب والدعوات على جهاز واحد للتحقق من أن المستودع عام وقابل للاستنساخ
- [ ] اطبع أوراق العمل الخمس (وكل ورقة على وجهين) + انسخ نماذج الحلول لنفسك
- [ ] افتح عرض الجلسة من `slides/` على شاشة العرض — ثلاث صيغ: `*.pptx` (تعديل + **ملاحظات محاضر** في Presenter View) و`html/index.html` (متصفح) و`pdf/*.pdf` (عرض بلا تعديل) — توزَّع رقمياً لا تُطبع
- [ ] جهّز بطاقات إجابة/تصحيح إلكترونياً أو ورقياً حسب بيئة المؤسسة
:::

:::check{ar="قبل الجلسة بعشر دقائق" en="Ten minutes before each session"}
- [ ] جهاز المدرّب موصول بالشاشة، والطرفية بخط كبير وواضح
- [ ] المتصفح مفتوح على صفحة المستودع + تبويب Pull requests
- [ ] ملاحظة على السبورة: «لا عمل على main» + رابط المستودع + رابط المرافق
- [ ] الأوراق المطبوعة لكل الطلاب على الطاولة
- [ ] فحص سريع للشبكة: `git ls-remote <url>` من جهازك
:::

:::box{type="info" ar="محاكاة بدون إنترنت (سكربت الإنقاذ)" en="Offline contingency plan"}
إذا سقط الإنترنت (شائع في القاعات)، لا تُلغِ الجلسة. استخدم **مستودعاً محلياً وهمياً**:
```text
# على جهاز المدرّب / instructor machine
$ mkdir -p /srv/remote.git && git init --bare /srv/remote.git
$ git remote add origin /srv/remote.git      # بدل رابط GitHub
$ git push -u origin main
```
تربط أجهزة الطلاب بالمجلد المشترك داخل الشبكة المحلية، فتكمل تدريبات الفروع والدمج
والتعارضات **كاملة** بلا أي وصول للإنترنت، ثم تُزامن الرفع إلى GitHub لاحقاً عندما يعود.
هذا أيضاً هو السكربت الذي وُلد منه هذا البرنامج، وقد استُخدم في توليد نماذج الحلول.
:::

## أزواج المراجعة (Review pairings)

:::bi
لا تدع الطلاب يختارون مراجعيهم بحرية تامة؛ الأصدقاء يتبادلون المدح. استخدم **دوران
(rotation)**: صفّ الطلاب، وكل طالب يراجع من يجلس بعيداً عنه. غيّر الاقتران في كل ورقة.
---EN---
Rotate reviewers deliberately. Friends swap praise; rotation produces real feedback.
:::

| الجلسة | نمط الاقتران | عدد المراجعين لكل طلب سحب | هدف المهارة |
|---|---|---|---|
| 3 | ثنائي (2 × 2) | 1 | كتابة أول مراجعة مكتوبة |
| 4 | ثلاثي حسب الأدوار (مطوّر + مختبر + كاتب) | 1–2 | مراجعة متخصصة |
| 5 | مراجعة مفتوحة (كل طالب على طلبين) | 2 | نقد تواريخ الدمج والنشر |

## سلّم تقييم جودة المراجعة (علّمه للطلاب قبل التطبيق)

| المستوى | الوصف | مثال جيد من مشروعنا |
|---|---|---|
| 5 نجوم | ملاحظة محددة + سؤال + اقتراح تعديل + احترام | «سطر 8: `fullName` اسم مختصر جداً، هل نضيف اسمك الكامل ليظهر صحيحاً في البطاقة؟» |
| 3 نجوم | ملاحظة صحيحة بلا اقتراح | «حقل `tags` فارغ» |
| نجمة | موافقة بلا تفصيل | «ممتاز» |
| صفر | نقد شخصي أو سخرية أو صمت | — |

:::box{type="rule" ar="قواعد التقدير التي أنصحك بإعلانها مسبقاً" en="Announce these marking rules up front"}
1. **الأدلة هي الحكم:** لا تحتسب مهمة بلا مخرجات أمر حقيقية من جهاز الطالب.
2. **المراجعة نصف الدرجة في الورقة 3، وربعها في 4 و5.** من لا يراجع لا يُقيَّم كامل الدرجة.
3. **الدقة التقنية يُسامح عليها، والمخالفات الأمنية لا:** نسيان أمر = مثال تعليمي؛ رفع
   `token` أو `--force` على فرع مشترك = خصم مباشر.
4. **الفهم العملي مقدَّم على الجمالية:** ملف بـ 4 مسافات في الأخطاء البصرية لا يُخصم
   عليه؛ ملف بلا التحقق (`node tests/validate-members.mjs`) يُخصم عليه.
5. **حق إعادة المحاولة:** لكل طالب إعادة تسليم واحدة خلال 48 ساعة على الأجزاء التي
   فشلت فقط، بشرط أن يرفق مخرجات جديدة.
:::

:::band{ar="5 · الأخطاء الشائعة وخطط التدخل" en="5 · Common failures & interventions"}
:::

| # | المشكلة | السبب الجذري | التدخل الفوري (2 دقيقة) | التدخل العميق |
|---|---|---|---|---|
| 1 | `fatal: not a git repository` | نُفّذ الأمر خارج مجلد المشروع | `pwd` ثم `cd ~/projects/class-team-hub` | علّمه علامة الفرع في الموجّه |
| 2 | `Author identity unknown` | لم يضبط `user.name/email` | `git config --global …` مباشرة | ربط بريده بحساب GitHub |
| 3 | الرفض `non-fast-forward` | لم يُحدّث الفرع | `git pull --rebase` ثم `push` | درس `fetch` في الورقة 04 |
| 4 | بطاقة لا تظهر في الصفحة | نسي `build-index.mjs` | `node tools/build-index.mjs` | شرح الملف المُولَّد |
| 5 | `<<<<<<<` في الملف المرفوع | حل تعارض ناقص | `grep -rn "<<<<<<<" .` ثم الإصلاح | مختبر الورقة 05 |
| 6 | JSON غير صالح (فاصلة زائدة) | كتابة يدوية بلا محرر JSON | `node tests/validate-members.mjs` | استخدام VS Code مع تلوين JSON |
| 7 | الطالب يدمج فرعه بنفسه | تجاوز عملية المراجعة | أوقف الدمج واطلب مراجعاً في الحال | خصم موثّق + مناقشة |
| 8 | عمل مشترك على جهاز واحد | قلّة الأجهزة | توزيع الأدوار: عضو تنفيذي + عضو موجّه | تخطيط بديل بمستودع مشترك محلي |
| 9 | «ضاع عملي» | `reset --hard` أو `restore` | `git reflog` ثم `git switch -c rescue <sha>` | درس التراجع في الورقة 04 |
| 10 | تعارض متكرر في نفس الملف | عدّلا نفس السطر في نفس الملف | أخبرهما بقاعدة تقسيم الملفات | إعادة توزيع المهام |
| 11 | «الفحص الأحمر أزعجني فرفعت بالقوة» | لم يفهم أن الحماية تحمي الفريق | أوقف الدفع، واعرض سبب الفشل على الشاشة | تدريبات الورقة 06 (كسر/إصلاح) |
| 12 | عدّل `validate-members.mjs` ليُخفي خطأه | سلوك غير مهني (تجاوز الفحص) | راجع تعديله وأعد الحالة | مناقشة فردية + خصم موثّق |
| 13 | الفحص يعمل عند الطالب ولا يعمل في CI | إصدار Node مختلف أو اعتماد على ملف غير متتبَّع | ثبّت إصدار Node في `setup-node` وتأكد من `git status` نظيف | درس: بيئة CI معزولة ونظيفة |

:::box{type="tip" ar="قاعدة الدقيقتين" en="The two-minute rule"}
أي مشكلة لم تُحلّ مع الطالب خلال دقيقتين: **سجّلها على السبورة في «طابور المشكلات»**،
وانتقل لغيره، ثم عالجها جماعياً في نهاية الجلسة. الطالب الذي يشغل المدرّب 15 دقيقة
يحرم 15 طالباً آخرين من التوجيه — وهذا نمط شائع في ورش البرمجيات.
:::

:::band{ar="6 · أسئلة متوقعة من الطلاب (وأجوبتك النموذجية)" en="6 · Expected questions"}
:::

| السؤال | الجواب المختصر الذي تعطيه |
|---|---|
| هل يمكن الرجوع بعد `commit` خاطئ؟ | نعم: قبل الرفع → `git commit --amend` أو `reset --soft`؛ بعد الرفع → `git revert`. والتزم كثيراً: كل التزام نقطة رجوع. |
| ما الفرق بين Git وGitHub بالضبط؟ | Git برنامج يراقب التغييرات على جهازك. GitHub موقع يستضيف مستودعات Git ويتيح التعاون. لا يعمل أحدهما بدل الآخر. |
| لماذا لا أرفع مباشرة إلى `main`؟ | لأن `main` هو النسخة التي يعتمد عليها الجميع؛ الفرع يحميك ويحمي الفريق حتى تُراجَع المساهمة. |
| هل أفقد عملي إن أخطأت في الأمر؟ | لا، إلا في `reset --hard` و`git clean -fd` و`restore` على تعديل غير مُلتزم. و`git reflog` يعيدك في معظم الحالات. |
| لماذا يظهر ملف `members-bundle.js` في كل تعديلي؟ | لأنه ملف مُولَّد آلياً من البطاقات. لا تعدّله يدوياً، وسيُعاد توليده مع الفهرس. |
| هل تعارض الدمج خطأ يجب تفاديه؟ | لا، التعارض رسالة طبيعية يقول فيها Git: «هنا تعديلان متضاربان، اختر أنت». مهارة حلّه هي محور الورقة 05. |
| كيف أعرف ما فعله زميلي؟ | `git log --oneline --graph --all` ثم `git diff` ثم `git blame`. وطلبات السحب على GitHub هي أوضح عرض لحالة العمل. |
| هل يمكن إلغاء طلب سحب؟ | نعم: `Close pull request` (يبقى التاريخ) أو استخدم `git revert` بعد الدمج. لا يوجد «حذف كامل» لسجل عام بل تصحيح معلن. |
| هل يجب أن يكون مستودعي عاماً؟ | لا في مشاريع العمل الخاصة، لكن في هذه الورشة نحتاج العام لأن GitHub Pages على حساب مجاني يعمل مع مستودعات عامة. |
| كيف أستمر بعد الورشة؟ | من أمثلة المهمة: أضف ميزة للموقع عبر فرع + طلب سحب، وشارك في مشروع مفتوح المصدر (`first-contributions`) لتمرين ممتع مماثل. |

:::box{type="warn" ar="لماذا يبقى مشروعنا هو الخيار الأول؟" en="Why our own project is still first choice"}
التدريب على مستودع جاهز يعلّم **الأوامر**. أما مشروع الفريق المخصّص فيعلّم **العمل
الجماعي المنظّم**: أدواراً حقيقية، ميزانية مراجعة، ملكية ملفات، وتعاقدات على التاريخ —
وهي المهارات التي يطلبها سوق العمل. لذلك: استخدم البدائل للتوسّع أو التعويض، وليس
كبديل أساسي. وإن لم يوجد سوى مستودع جاهز، أضف عليه خطوة إضافية: اطلب من كل طالب إضافة
ملف باسمه في مجلد `students/` ليعيش تجربة «ملفي لا يتعارض مع ملفاتكم».
:::

قبل أن يمدحوا، ويقرؤون مخرجات الأوامر قبل أن يخمّنوا. صمّم تدخّلك حول هذا الهدف، وستجد
أن بقية المهارات التقنية تأتي تلقائياً معه.
