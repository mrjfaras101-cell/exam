هذه أهم ورقة في البرنامجThe most important worksheet

هنا ينتقل الطالب من «التعلّم عن Git» إلى العمل بمنهج فريق حقيقي. فتّش في تصحيحك عن ثلاثة أشياء بالترتيب: (1) هل التزم بالفرع وطلبه؟ (2) هل الالتزامات واضحة ومفيدة؟ (3) هل شارك في المراجعة بجدية (مكتوبة ومحدّدة) أم كتب «موافق»؟ التقييم يجب أن يرفع وزن المراجعة، لأنها المهارة التي تحوّل الطالب إلى عضو فريق لا مجرد كاتب كود.

This is where students become team members. Prioritise three things: did they follow the branch + PR workflow, are their commits meaningful, and did they review a teammate's work substantively — not a bare “LGTM”.

جدول التقييم المُجمَّعMarking rubric
# المهمة النقاط معيار القبول الأساسي ملاحظة تصحيح
1 مزامنة + Issue 10 رقم Issue حقيقي في مستودع الفريق Issue مفتوح بوصف واضح
2 إنشاء الفرع 10 الاسم مطابق للاتفاقية feature/<user>-card خصم على أسماء غامضة
3 ملف البطاقة + الفحص 20 validate-members.mjs = 0 خطأ الفحص هو الحكم لا الشكل
4 الالتزام والرفع 20 التزام برسالة صحيحة + push -u ناجح يقيس جودة الرسالة فعلياً
5 طلب السحب + المراجعة 20 PR مكتمل + مراجعة زميل مكتوبة نصف الدرجة للمراجعة
6 الاستجابة للملاحظات 10 التزام إضافي على نفس الفرع بعد ملاحظة يقيس مهارة العمل الجماعي
— الأسئلة (س1–س4) 10 — إجابة عملية لا نظرية
معيار «المساهمة الكاملة»Full-contribution standard

لا تُمنح درجة كاملة لمن لم يُدمج أو لم يُراجع. الحد الأدنى للتسليم المقبول: بطاقة صحيحة مدموجة/تحت المراجعة، + مراجعة مكتوبة واحدة على عمل زميل. المراجعة ليست إضافية — هي نصف قيمة هذه الورقة.

إجابات المهامTask solutions
1
المزامنة والمهمة (Issue)
Sync and issue
◆ قبول★ 10 نقطة

معيار القبول: مخرجات git pull --ff-only (يُقبل Already up to date) + رقم Issue حقيقي يمكن فتحه.

الإجابة النموذجية:

$ git switch main
$ git pull --ff-only
remote: Enumerating objects: 12, done.
Updating 8de1e7a..a1b2c3d
Fast-forward
 data/members/ali-h.json | 9 +++++++++
 1 file changed, 9 insertions(+)

أخطاء متوقعة: بدأ العمل مباشرة دون سحب → −4 (وسيظهر أثره كتعارض في الورقة 05). عنوان Issue عام («مهمة») → −2. لم يفتح Issue إطلاقاً → −6 مع السماح بفتحه أثناء الجلسة.

طريقة تحقّق سريعةFast verification

افتح تبويب Issues في مستودع الفريق: يجب أن ترى عدداً من المهام يقارب عدد الطلاب، وعنوان كل مهمة يذكر اسم المستخدم. هذا يثبت أن الجميع بدأ من نقطة صحيحة — وتكلفته 30 ثانية.

2
إنشاء الفرع
Create the branch
◆ قبول★ 10 نقطة

معيار القبول: اسم فرع بصيغة type/username-topic وحروف إنجليزية صغيرة وشرطات فقط، مع نجمة * على الفرع الصحيح في git branch.

أمثلة مقبولة: feature/omar-qa-card · feat/omar-qa-card · add/omar-qa-card أمثلة مرفوضة وخصوماتها:

الاسم المشكلة الخصم
my-branch لا يدل على صاحبه ولا موضوعه −3
omar_card شرطة سفلية (المعيار = شرطات) −1
فرع-عمر حروف عربية ومسافات تسبب مشاكل في الأدوات −2
omar/final/final2 مسارات متعددة وتسمية فوضوية −2
main (عمل على الفرع الرئيسي) مخالفة جسيمة −10 وإعادة فورية

مهارة يجب التحقق منها: أن يعرف الطالب الإجابة على «على أي فرع أنا الآن؟» — إما git branch أو git branch --show-current أو git status -sb.

3
ملف البطاقة والفحص
Card file and validation
◆ إتقان★ 20 نقطة

معيار القبول القاطع: مخرجات --- النتيجة / Result: 6 بطاقة، 0 خطأ، 0 تحذير ---. التحذيرات لا تمنع القبول لكنها تستحق ملاحظة تصحيح.

مثال بطاقة صحيحة:

{
  "fullName": "عمر القاسم",
  "github": "omar-qa",
  "role": "مختبر QA",
  "favoriteCommand": "git log --oneline --graph --all",
  "message": "أبحث عن الأخطاء قبل أن يجدها المستخدم، وأثبت كل إصلاح بمخرجات واضحة.",
  "tags": ["Testing", "JavaScript"],
  "joinedAt": "2026-10-06"
}

خريطة الأخطاء التي يكتشفها الفحص ورموزها:

رسالة الفحص السبب الدرجة
حقل مفقود: "message" الحقل غير موجود أو فارغ −4
اسم مستخدم غير صالح حرف كبير أو _ أو رموز −3
الامر المفضل يجب ان يبدا بـ "git " كتب ls أو npm start −3
طول الرسالة 8 — يجب أن يكون بين 10 و140 رسالة قصيرة جداً −2
دور غير معتاد دور خارج القائمة المعتمدة −2 (تحذير فقط)
بيانات حساسة أو ممنوعة بريد/هاتف/كلمة مرور −8 + تحقيق
البطاقة غير مُفهرسة لم يُنفّذ build-index.mjs −4
اسم مستخدم مكرر مع انتحل اسم زميل −10 + إعادة
اسم الملف لا يطابق اسم المستخدم my-card.json بدل omar-qa.json تحذير −1
تنبيه إلزامي على بيانات شخصيةMandatory personal-data check

افحص كل بطاقة بعينك بحثاً عن: بريد شخصي، رقم هاتف، عنوان سكن، اسم مدرسة/جامعة مع تفاصيل تعريفية، اسم أحد الوالدين. أي واحدة منها تُحذف من ملف موجود في مستودع عام — وهذا جزء من تدريبهم على الخصوصية الرقمية. إن تجاوزت الفحوص ولم تكتشفها، فالمسؤولية على المشروع.

4
الالتزام والرفع
Commit and push
◆ إتقان★ 20 نقطة

معيار القبول: التزام برسالة بصيغة Conventional Commits + نجاح git push -u + git branch -vv يُظهر الربط [origin/feature/...].

الإجابة النموذجية:

$ git add data/members/omar-qa.json data/members-index.json data/members-bundle.js
$ git commit -m "feat(members): add card for omar-qa"
[feature/omar-qa-card 89f5cff] feat(members): add card for omar-qa
 3 files changed, 25 insertions(+), 2 deletions(-)
 create mode 100644 data/members/omar-qa.json

$ git push -u origin feature/omar-qa-card
 * [new branch]      feature/omar-qa-card -> feature/omar-qa-card
branch 'feature/omar-qa-card' set up to track 'origin/feature/omar-qa-card'.

سلّم تقييم رسالة الالتزام (أهم 6 نقاط في المهمة):

المستوى مثال النقاط
ممتاز feat(members): add card for omar-qa 6
جيد feat: add omar card 4.5
مقبول add my card file 3
ضعيف update / changes / add 1
مرفوض final / asdf / . / . / رسالة فارغة 0

أخطاء متوقعة:

الخطأ العلاج الخصم
التزم لكن لم يرفع أهم خطأ — اسأله: «أين عملك الآن؟» −6
رفع على main تحقّق أنه يحترم حماية الفرع −10
التزامان برسالتين فوضويّتين لنفس الملف يقبل 3 نقاط من 6 للرسائل −3
git add . وحده أضاف ملفات غير مقصودة −2 مع مناقشة الدرس
نسخ مخرجات الورقة بدل مخرجات جهازه صفر في المهمة + تحقيق شفافية −20
استخدم --force بلا سبب ذكر توجيه الورقة 05 −3
كيف تكتشف أدلة منسوخة من الورقة؟Spotting copy-paste evidence

علامات واضحة: مخرجات المهمة الرقم 4 يظهر فيها بريد nour@example.com أو hash مطابق تماماً لحروف الورقة (89f5cff)، أو اسم بطاقة لعضو آخر، أو رسالة feat(members): add card for omar-qa بينما الطالب اسمه سارة. اطلب منه تنفيذ الأمر أمامك في جولة سريعة، وسجّل ملاحظة «دليل غير شخصي» تخصم فيه من بند الأدلة (لا من فهمه التقني).

5
طلب السحب والمراجعة
Pull request and review
◆ إتقان★ 20 نقطة

معيار القبول — خمسة عناصر، كل عنصر 4 نقاط:

# العنصر ما أراقبه
1 PR مفتوح للفرع الصحيح base: main ← compare: feature/<username>-card
2 عنوان مطابق للاتفاقية نفس صيغة رسالة الالتزام
3 القالب مملوء ماذا تغيّر + الأدلة + طريقة الاختبار
4 Closes #<issue> مذكور يربط المهمة بالطلب
5 مراجعة زميل مكتوبة ومحدّدة تعليق على ملف أو سطر، لا «موافق»

سلّم تقييم جودة المراجعة (بند حرج — 6 نقاط):

المستوى مثال تعليق النقاط
ممتاز «سطر 6: الأمر npm start لا يبدأ بـ git، هل تقصد git status؟ اقترح تعديلاً.» 6
جيد «الحقل message أقل من 10 أحرف، يُفضّل توضيح أدوارك.» 4.5
مقبول «البطاقة صحيحة، لكن الوسوم فارغة — ممكن تضيف JavaScript؟» 3
ضعيف «ممتاز ✅» 1.5
مرفوض لا تعليق / «موافق» / نقد شخصي 0

أخطاء متوقعة: - دمج الطالب فرعه بنفسه (Merge pull request) → −15 (بند صريح في الورقة). - كتابة التعليق بلغة غير مهنية أو سخرية → −6 + جلسة إرشاد. - مراجعة PR لنفسه (لا فائدة) → 0 في هذا البند. - لم يطلب Reviewer محدداً → −2.

سكربت الجولة السريعة على GitHub (3 دقائق لكل فريق)Fast GitHub tour

لكل طالب: افتح صفحته github.com/<username> → تبويب Activity أو سجّل الدخول إلى المستودع ← Pull requests ← صفِّ بـ author:<username>. تحقّق من: العدد، العنوان، المراجعات، ومن فتح PR ولم يُدمج. هذا يعطيك لوحة تقييم حقيقية بلا أوراق.

6
الاستجابة للملاحظات
Responding to feedback
◆ سلوك مهني★ 10 نقطة

معيار القبول: التزام إضافي على نفس الفرع بعد ملاحظة المراجع + طلب السحب تحدّث تلقائياً (لا يُنشأ PR جديد).

$ git add data/members/omar-qa.json
$ git commit -m "fix(members): add JavaScript tag per review feedback"
[feature/omar-qa-card 3c7d9e1] fix(members): add JavaScript tag per review feedback

$ git push
   89f5cff..3c7d9e1  feature/omar-qa-card -> feature/omar-qa-card

أخطاء متوقعة: فتح PR جديد للتعديل الصغير (0) — علّمه أن PR الجديد يفقد سياق المراجعة. الاعتراض على الملاحظة بلا تنفيذ ولا شرح مقنع (3 من 10). الالتزام برسالة fix واضحة وبدون تفصيل كافٍ (6 من 10).

مؤشر نضج مهني — راقبهProfessional maturity signal

الطالب الذي يرد على الملاحظة بـ «رأيك صحيح، عدّلتُ الملف والتزمت، وما زلت أعتقد أن الوسم إضافي لكن لا مشكلة» — هذا أعلى مستوى في الورقة الثالثة: يتقبّل النقد، ينفّذ، ويحافظ على رأيه باحترام. اذكر هؤلاء في تقرير الفريق.

إجابات الأسئلةKnowledge-check answers
س1
-c في switch
switch -c
◆ فهم★ 2.5 نقطة

git switch -c feature/x تُنشئ فرعاً جديداً وتنتقل إليه في خطوة واحدة. أما git switch feature/x فتنتقل إلى فرع موجود مسبقاً فقط، وستفشل إن لم يكن موجوداً (fatal: invalid reference).

س2
لماذا المزامنة قبل الفرع
Why sync first
◆ تحليل★ 2.5 نقطة

لأن الفرع الجديد يتفرّع من النقطة الحالية لـ main. فلو كان main قديماً، فستبني عملك على أساس ناقص، وسيظهر لاحقاً كتعارض أو كعدد هائل من «الالتزامات الغريبة» في طلب سحبك، وسيضطر المراجع للمقارنة مع نسخة قديمة.

س3
معنى Closes #12
Closes #12
◆ استخدام★ 2.5 نقطة

تعني «هذا الطلب يُنهي المهمة رقم 12» — فيربط GitHub الطلب بالمهمة، وينشئ مرجعاً تلقائياً في الطرفين، ويُغلق المهمة تلقائياً عند دمج طلب السحب. فائدتها: تنظيم، وإثبات أن العمل استهدف مهمة معروفة، ومنع العمل المهدور على مهام منتهية.

س4
رسالة التزام صحيحة
Write a valid commit
◆ تطبيق★ 2.5 نقطة

الإجابة النموذجية: fix(ui): correct card alignment on mobile (مقبول أيضاً: fix(css): fix card alignment on mobile screens).

معيار الدرجة: 1 نقطة للنوع fix، نقطة للنطاق (ui) أو (css)، ونصف لوصف واضح بصيغة الأمر وبالإنجليزية. رسالة عربية بلا نوع → نصف الدرجة فقط.
